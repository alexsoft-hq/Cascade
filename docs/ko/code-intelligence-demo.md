# 0.9 코드 작업 공간 확인하기

Java·TypeScript·프런트엔드 프로젝트를 분석한 뒤 확인합니다. Cascade는 소스를
읽으며, 대상 애플리케이션을 실행하거나 의존성을 설치하지 않습니다.

## MCP에서 에이전트 작업부터 확인하기

MCP 클라이언트가 stdio로 `cascade mcp --root /path/to/project`를 실행하도록
연결한 뒤, 다음처럼 구체적인 작업을 요청합니다.

> Cascade로 계좌 생성 시 초기 잔고를 처리하는 위치를 찾아줘.
> session_briefing에서 시작해 관련 선언과 정확한 원문을 읽고,
> 영향을 받는 API와 테이블을 근거·소스 위치와 함께 설명해줘.
> 미확인 관계와 결과가 잘린 부분도 밝혀줘.

기본 순서는 `session_briefing` → `code_search` / `code_context` →
`file_outline` → `code_snippet`입니다. 데이터 동작을 바꾸는 작업은 이어서
영향도 도구로 확인합니다. 응답마다 `basis.project`, `basis.freshness`,
분석 범위, 신뢰 수준과 생략 여부를 확인해야 합니다. 여러 프로젝트를 제공한다면
`projects`로 목록을 읽고 이후 조회에 프로젝트를 명시합니다.
`index_status`는 마지막 확인 상태를 보여 주며, 실제 조회가 최신성 검사를 수행합니다.
영향도 조회는 작은 `limit`에서 시작하고 필요한 영역별 생략 수와 다음 페이지를
확인합니다. 표시한 경로가 줄었다고 실제 영향이 적다고 해석하면 안 됩니다.

함수를 추가·이름 변경·삭제하고 저장한 뒤 에이전트에게 다시 검색시킵니다.
새 세대의 답이나 명시적인 실패가 나와야 하며, 이전 답을 최신이라고 재사용하면 안 됩니다.
LLM 대화 자체의 기억은 별개이므로 수정 후에는 반드시 재조회해야 합니다.
아래 웹 화면은 같은 도구 결과를 사람이 살펴보는 보조 수단입니다.

## 웹 화면 열기

```sh
cascade init --root /path/to/project
cascade analyze --root /path/to/project
cascade view --root /path/to/project --port 4319
```

[로컬 코드 작업 공간](http://127.0.0.1:4319/#tab=code)을 엽니다.
원하는 파일이 빠졌다면 분석할 때 `--java-src`, `--ts-src`, `--web-src`로
입력 경로를 지정합니다. 자세한 옵션은 [CLI 문서](../cli.md)에 있습니다.

## 1. 브리핑으로 시작하기

**Code(코드)**에서 프로젝트 브리핑과 최신성·분석 범위를 읽고 복사합니다.
새 AI 세션에 전달할 짧은 설명에 구조, 기록된 진입점, 한계가 포함되는지 봅니다.
진입점이 없으면 해당 분석에서 기록하지 못한 것이며, 파일 이름으로 추측하지 않습니다.

에이전트는 `session_briefing` 도구로 같은 답을 받을 수 있습니다.

```sh
cascade code briefing --root /path/to/project --max-bytes 12288
```

## 2. 모듈 연결 따라가기

의존 관계 목록에서 출발 디렉터리, 도착 디렉터리, 관계 종류를 확인합니다.
근거를 펼치면 연결에 쓰인 파일을 볼 수 있습니다. import와 호출 관계를 구분하며,
호출은 기록된 근거 수준을 유지합니다. 디렉터리 묶음은 경로 기준의 정리이며,
업무 모듈 경계라고 단정하지 않습니다. 미확인·외부 대상과 생략된 결과도 표시합니다.
모노레포 내부 연결은 **디렉터리 깊이**를 늘려 확인합니다. 점검한 Ghostfolio에서는
깊이 5가 내부 모듈을 살펴보기에 적합합니다.

```sh
cascade code architecture --root /path/to/project --depth 2 --limit 50
```

## 3. 선언 찾고 정확한 원문 읽기

프로젝트의 함수나 클래스 이름을 검색합니다. 결과를 열어 파일의 선언 목록을
확인하고, 선언을 선택해 원문을 읽습니다. 긴 시그니처와 코드는 패널 안에서
가로로 스크롤합니다. Java 오버로드는 별도 항목으로 나타납니다. 같은 이름이
여럿이면 검색 결과의 정확한 선언 ID를 선택합니다.

```sh
cascade code search --root /path/to/project --query OrderService
cascade code outline --root /path/to/project --file src/orders.ts
cascade code snippet --root /path/to/project --symbol '<검색 결과의 선언 ID>'
```

원문이 크기 제한으로 잘렸는지 표시를 확인합니다. 정확한 범위가 없는 과거 분석은
재분석하거나 파일의 줄 범위를 지정해야 합니다. 현재 파일과 기록한 해시가 다르면
검증된 원문으로 보여 주지 않고 오류가 나야 합니다.

## 4. 저장 후 자동 갱신 확인하기

분석 경로 안의 파일에 이름이 있는 함수를 추가하고 **저장한 뒤** 새 이름을 검색합니다.
조회는 필요한 분석이 끝날 때까지 기다립니다. 원문을 열어 저장한 내용이 보이는지
확인합니다. 이름을 바꾸거나 함수를 삭제한 뒤 다시 검색하면, 다음 정상 갱신 후
기존 선언이 사라져야 합니다. 화면에 이미 표시된 브리핑은 코드 작업 공간의
새로고침으로 다시 읽습니다. 화면은 조회 결과를 보여 주며 편집기 버퍼가 아닙니다.
다음 조회에서 구조 세대가 달라졌다면 기존 개요는 최신성 알 수 없음으로 표시되고,
새로고침 전까지 브리핑 복사가 비활성화됩니다. 백그라운드 검사는 30초마다 실행하며,
조회는 이 주기를 기다리지 않고 답변 전에 확인합니다.

```sh
cascade code search --root /path/to/project --query yourNewFunction
cascade code status --root /path/to/project
```

스냅샷 동작은 다른 포트에 `--no-watch` 뷰어를 띄워 비교할 수 있습니다.
최신성은 알 수 없음으로 표시되고, 원본이 달라진 코드 조각은 거절합니다.
편집기의 미저장 내용은 분석하지 않습니다.
전체 계약은 [코드 구조와 최신성](../code-intelligence.md)을 참고하세요.
